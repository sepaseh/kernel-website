# تحویل تغییر و برنامهٔ پیاده‌سازی

[English](change-workflow.md) · [فارسی](change-workflow.fa.md)

این الگو را برای قابلیت، نقص یا تغییر ابزار استفاده کنید. سند برنامه‌ریزی قابل‌حمل
است، نه runtime هوش مصنوعی یا الزام به دستیار خاص. نسخهٔ پُرشده را کنار شاهد محلی
وظیفه یا issue و PR مجاز نگه دارید. ایجاد فرادادهٔ بیرونی، پیام، commit و انتشار
برای اثر واقعی خود به مجوز نیاز دارند.

## قرارداد تغییر را مشخص کنید

- درخواست، منبع و تاریخ را ثبت و الزام، پیشنهاد، شرط و خارج از محدوده را جدا
  کنید. موضوع نقشهٔ راه به‌تنهایی نیاز محصول نیست.
- مخزن و مالک سورس و مصرف‌کنندهٔ HTTP درگیر را نام ببرید. قرارداد و کاتالوگ محلی
  متعلق به این پروژه است؛ در صورت نیاز سازگاری قابل مشاهدهٔ HTTP را هماهنگ کنید.
- [ناوبری](source-navigation.fa.md)، سورس کامل مالک، قرارداد، قاعده و آزمون را
  بخوانید. رفتار و نقص فعلی، شامل تغییر مرتبطِ ثبت‌نشده یا untracked، را بدون
  خواندن محیط واقعی، state خصوصی یا اسرار ثبت کنید.
- سناریوی پذیرش قابل مشاهده بنویسید: محرک، نتیجه، مرز خطا و مجوز و روش بررسی.
  رقابت نشست، حریم خصوصی زبان و cache و بازیابی مرتبط را پوشش دهید.
- مرحلهٔ انتشار را مشخص کنید. مرحلهٔ فعلی صفحهٔ قابل اجرا، CSS، fixture مرورگر
  یا استقرار ندارد؛ یکپارچه‌سازی آینده را تکمیل‌شده نشان ندهید.

## الگوی قابل استفاده

این الگو را کپی و پُر کنید. جای خالی، شاهد تکمیل کار نیست.

```text
درخواست، منبع و تاریخ:
الزام‌ها و موارد صریحِ خارج از محدوده:
مالک و مصرف‌کنندگان درگیر:
commit یا tree مبنا و محدودهٔ تغییر ثبت‌نشده یا untracked:
R1: با پیش‌شرط ... وقتی ... آنگاه ...؛ بررسی با ...
R2: حالت نامعتبر، قدیمی یا بدون مجوز ... نباید ...؛ بررسی با ...
وابستگی یا تصمیم اپراتورِ باقی‌مانده:
گام‌های کوچک و مرتب پیاده‌سازی و فایل مالک:
سازگاری HTTP و داده و روش بازگشت:
fixture ساختگی، منابع متعلق به آزمون و پاک‌سازی:
شناسه و پروفایل از .agents/validation.json:
بررسی دستی یا بیرونیِ اجرا‌نشده:
نتیجهٔ مشاهده‌شده، نخستین شکست، بازتولید و skip:
پیشنهاد باقی‌مانده و مالک:
```

کوچک‌ترین پیاده‌سازی منسجم را ترجیح دهید. رفتار API در سرویس و نمایش در وب‌سایت
بماند. یکپارچه‌سازی محصول یا سرویس بیرونی به نیاز واقعی احتیاج دارد. تغییر ماندگار
معماری را در ADR ثبت و توضیح متناظر انگلیسی و فارسی را به‌روز کنید.

دستور را از [manifest مرجع](../.agents/validation.json) و
[سیاست مشارکت](../CONTRIBUTING.fa.md) انتخاب کنید و گیت کامل موازی نسازید. تغییر
سورس، workflow تنظیم‌شده و بررسی واقعاً اجراشده را جدا ثبت کنید. شاهد نخستین شکست
را حفظ، با ورودی ساختگی بازتولید و اصلاح را توضیح دهید؛ شکست را با تلاش دوباره،
skip، suppression یا کاهش آستانه پنهان نکنید. از بررسی سورس، بازبینی دستی
screen reader، نتیجهٔ میزبانی‌شده، بازیابی تولید یا benchmark دستیار نتیجه نگیرید.
