# Website testing and evidence

[English](testing.md) · [فارسی](testing.fa.md)

Use the [canonical manifest](../.agents/validation.json) for commands and
[validation](validation.md) for scope and sequencing. The **delivery-tooling**
phase has an exact 303-file inventory and remains non-runnable with
applicationReady:false. Its 66 production modules, 34 source test files and three
source test-support modules are unchanged. Four retained integration helpers with
three Node owner-test files and eight delivery helpers with six Node owner-test
files add no application entry point or browser/API/Docker launcher.

| Layer               | Published evidence and limits                                                                                                                                                                            |
| ------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Local product       | Real React/RTL and supporting libraries, HTTP/session code and synthetic Requests/Responses test forms and support. Framework/document navigation has documented mocks.                                  |
| Catalogs/fonts      | Ten complete flat catalogs, real ICU parsing and explicit client selections; actual font binaries, generated bytes, metadata and measured Python coverage. No browser shaping/loading result is implied. |
| Governance/tools    | Snapshot/import/CI/guidance guards, portable hooks and owner tests for explicit API location, bundle data/budgets and performance/visual environment helpers.                                            |
| Delivery contracts  | Artifact copying/packaging, readiness guards, public configuration, explicit health targets, cleanup and target validation use owned synthetic files, injected operations or owned loopback listeners.   |
| Audit regression    | The existing eleven audit regression cases remain in measured Vitest unit coverage; they are not moved to the Node governance runner.                                                                    |
| Runtime integration | Pages, layout/CSS, browser journeys, API launchers, actual screenshot comparisons, Lighthouse and deployment remain deferred.                                                                            |

The retained integration owners are [API location](../scripts/api-repository.test.mjs),
[performance helpers](../scripts/website-performance.test.mjs) and
[visual helpers](../scripts/visual-environment.test.mjs). They use owned disposable
fixtures. A synthetic project manifest or build graph tests validation behavior;
it is not an installed API, actual Next build, screenshot or lab measurement.

The eight delivery helpers own [shared file/readiness policy](../scripts/release-files.mjs),
[standalone preparation](../scripts/prepare-standalone.mjs),
[packaging](../scripts/package-release.mjs),
[configuration validation](../scripts/validate-deployment-env.mjs),
[public template rendering](../scripts/render-deployment.mjs),
[explicit health checks](../scripts/healthcheck.mjs),
[owned cleanup](../scripts/docker-smoke-cleanup.mjs) and
[target validation](../scripts/validate-workflow-targets.mjs). Their six measured
Node owner files are [file policy](../scripts/release-files.test.mjs),
[preparation](../scripts/prepare-standalone.test.mjs),
[packaging](../scripts/package-release.test.mjs),
[configuration/health/template contracts](../scripts/deployment.test.mjs),
[cleanup](../scripts/docker-smoke-cleanup.test.mjs) and
[target contracts](../scripts/validate-workflow-targets.test.mjs). The complete
eleven-check gate includes all nine integration/delivery Node owner files; the
existing [audit tests](../scripts/run-audit.test.mjs) keep their Vitest unit owner.

Core delivery CLIs require the unlinked public readiness marker before operations
and refuse this false phase. Copy/package tests explicitly mark owned synthetic
roots ready; that tests file behavior, not the missing application. Configuration
tests inject public values, health tests use owned loopback listeners, and cleanup
tests inject fake Docker/Compose callbacks. No real dotenv, engine, TLS service,
browser or operator environment is used. [Delivery](deployment.md) and
[operations](release-operations.md) describe the inert references and later acceptance.

The API resolver requires KERNEL_SYNTHETIC_ENV=1 and an explicitly selected absolute
KERNEL_API_DIRECTORY. It validates selected project markers without a sibling
fallback. It does not install, launch or attest an immutable fixture's readiness.
A future independently installed API fixture needs its own verified revision and
contract before runtime evidence. Existing developer services and operator state
are never fixtures.

Record command, exact source scope/revision, first failure, result, failures/skips,
coverage and cleanup. Local checks, hosted provider checks, manual assessment and
dated history are different records. Follow [test reliability](test-reliability.md).
Before runnable publication, add and observe genuine build, browser, both CSP-mode
and compatible visual checks. Local tests do not establish SSR, browser cookies,
complete accessibility, deployment, production OTP or field performance.
