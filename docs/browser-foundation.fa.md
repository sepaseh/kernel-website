# پایهٔ مرورگر و سناریوهای نوشته‌شده

[English](browser-foundation.md) · [فارسی](browser-foundation.fa.md)

## مرحلهٔ سورس و شواهد

پایهٔ مرورگر سناریوهای نوشته‌شده با SDK را پیش از فعال‌سازی برنامه معرفی کرد. برای موجودی دقیق فعلی [نشانگر سورس](../.github/bootstrap-policy.json) و برای پذیرش [قرارداد برنامه](application.fa.md) را بخوانید. نسخهٔ application صفحه‌ها، چیدمان ریشه و CSS را با `applicationReady:true` و نمایهٔ پانزده‌بررسی یکپارچه می‌کند. آزمون مالک Node و سناریوی نوشته‌شدهٔ نوع‌سنجی‌شده همچنان فقط لایهٔ خود را می‌سنجد؛ اجرای واقعی مرورگر و API و مقایسهٔ تصویری سازگار باید برای درخت دقیق برنامه جداگانه ثبت شود.

[نمونهٔ مستقل API](api-fixture.fa.md) نسخهٔ عمومی ثابت، بررسی هویت نصب، وضعیت تازهٔ
تحت مالکیت، قرارداد پورت اجراکننده و کنترل worker در SDK را تعریف می‌کند. این
بررسی‌های API مکمل بررسی SDK مرورگر در پایین هستند؛ آزمون مالک مصنوعی آن‌ها
سازگاری واقعی قرارداد ارتباطی را ثابت نمی‌کند.

پیش از خواندن مقدار محیط، فایل SDK نصب‌شده یا مقصد عملیات، بارگذاری را رد می‌کند.

علامت‌گذاری‌شده و برنامهٔ Node دورریختنی متعلق به خود آزمون استفاده می‌کند و نشانگر
سورس را تغییر نمی‌دهد.

## مرز وابستگی و ورودی

Playwright و اتصال Axe وابستگی توسعهٔ محلی با نسخهٔ دقیق‌اند. [نوع‌سنجی سخت‌گیرانهٔ ابزار](../tsconfig.tooling.json) هر سیزده فایل TypeScript تألیف‌شدهٔ e2e و چهار تنظیم را با نوع SDK نصب‌شده بررسی می‌کند. این کامپایل از آماده‌سازی و اجرای مرورگر جداست. نمایهٔ برنامه فرمان واقعی مرورگر وب‌سایت، CSP اجرایی و گزارش‌محور و تصویر را همراه ساخت و بودجه و تحلیل کد بلااستفاده ثبت می‌کند. Lighthouse، staging و DAST بیرونی و استقرار پذیرش عملیاتی جداگانه و موکول‌شده دارند.

حل‌کننده، نام بستهٔ ریشهٔ انتخاب‌شده، نسخهٔ دقیق اعلام‌شدهٔ Playwright، ورودی
lockfile، نام و نسخهٔ بستهٔ نصب‌شده و ورودی ثابت و بدون پیوند CLI را بررسی می‌کند.
probe تصویری، ورودی ثابت ماژول محلی را نیز حل می‌کند. این بررسی ساختاری، محتوای
دلخواه بایت‌های بسته، فایل اجرایی مرورگر، نسخهٔ API یا سازگاری قرارداد ارتباطی را
تأیید نمی‌کند. SDK سراسری یا ریشهٔ والد جایگزین نمی‌شود.

ورودی مصنوعی وب‌سایت و API به مبدأهای متعارف، متمایز و صریح HTTP روی IPv4
loopback با پورت غیرصفر نیاز دارد؛ میزبان و پورت وب‌سایت باید سازگار باشند،
indexing صریحاً خاموش باشد و `KERNEL_SYNTHETIC_ENV=1` همراه با
`KERNEL_API_DIRECTORY` مطلق و صریح ارائه شود. API انتخاب‌شده باید [قرارداد محل نمونه](../scripts/api-repository.mjs) و بررسی نسخهٔ مستقل Git و نصب را برآورده کند و از src/index.ts منتشرشده به‌عنوان ورودی استفاده کند. نسخهٔ همسایه ضمنی کشف نمی‌شود.

فقط تنظیم عمومی اعلام‌شده و نیازهای ضروری اجرا به فرزند تحت مالکیت می‌رسند؛
state خصوصی، اعتبارنامه و `NODE_OPTIONS` ورودی آزمون نیستند.
خود Playwright محیط فرایند والد را با محیط فرزند web-server ادغام می‌کند؛ دیکشنری
`env` در تنظیم فقط مقدار را اضافه یا جایگزین می‌کند. بنابراین هر چهار ورودی
اجرایی از `loadPlaywrightConfig` استفاده می‌کنند. این مرز پس از آمادگی و پیش از
خواندن مقدار عمومی یا خصوصی، SDK یا مقصد، نام کلیدهای والد را بررسی می‌کند.
کلید ناشناخته، `NODE_OPTIONS` و هوک تغییر سورس Playwright بدون خواندن مقدارشان
رد می‌شوند. فقط کنترل‌های SDK که جداگانه و صریح اعلام شده‌اند مجازند.
Windows نیز مجموعهٔ ثابتی از نام‌های مربوط به هویت و مسیر سیستم‌عامل را به فرزند
تازه اضافه می‌کند؛ فقط همین نام‌های دقیق ضروری و فقط در Windows مجازند و مقدار
آن‌ها بررسی نمی‌شود. دیکشنری فیلترشده به‌تنهایی این context سیستم‌عامل را حذف
نمی‌کند. اجرای مستقیم SDK وب‌سایت باید والد صریحاً فیلترشده داشته باشد؛ همان کاری
که اجراکنندهٔ تصویری و CSP متعلق به پروژه انجام می‌دهند.
`createPlaywrightConfig` کارخانهٔ داده است و جایگزین این مرز اجرایی نیست.

پذیرش برنامه به آماده‌سازی مرورگر مطابق نسخه نیاز دارد؛ فرزندان تصویری از محل
مرورگر محلیِ نصب انتخاب‌شده استفاده می‌کنند. نصب SDK با npm یا اجرای probe ساختگی
در آزمون مالک، آماده‌بودن مرورگر را ثابت نمی‌کند.

تنظیم وب‌سایت و تصویر، fixture تازه و متعلق به آزمون را برای API و وب‌سایت توصیف
می‌کند و سرویس موجود را دوباره به کار نمی‌گیرد. ابزار سناریوها مبدأ خود را از
ورودی عمومی صریح و بررسی‌شده می‌گیرد و پورت ثابت یا سرویس موجود را جایگزین نمی‌کند.
انتظار مربوط به مدیر seedشده و کد OTP، شرط پذیرش fixture در آینده است. پیش از
اجرای واقعی، این شروط باید با API مستقلاً نصب‌شده در یک revision تغییرناپذیر
تطبیق داده شوند.

تنظیم smoke و staging پس از آمادگی به میزبان و مقصد صریح و مجاز وب‌سایت و API
نیاز دارد. در smoke، شناسهٔ استقرار انتخاب‌شده باید با شناسهٔ مورد انتظار یکسان
باشد. سناریوی عملیات این دادهٔ بررسی‌شده را از فرادادهٔ تنظیم می‌گیرد. ساخت داده
مجوز تماس با محیط اپراتور نیست؛ اجرای واقعی عملیات به مجوز و شاهد پذیرش مستقل
خود نیاز دارد.

## سناریوهای نوشته‌شده و شواهد تصویری

نه فایل سورس سناریوی [وب‌سایت](../e2e/website/website.spec.ts)، بررسی احراز هویت و
حساب، جداسازی نشست، مرز کلاینت، زبان و جهت، SEO، CSP، دسترس‌پذیری، فونت و کارایی
را شرح می‌دهند. [ابزار مشترک fixture](../e2e/website/helpers.ts) زیرساخت تست است.
فرایند standalone اضافی در سناریوی SEO از مالک بازبینی‌شدهٔ آمادگی، فایل بدون
پیوند و چرخهٔ فرزند مستقیم استفاده می‌کند. رفتار صفحه به اجرای واقعی روی درخت
پیشنهادی برنامه نیاز دارد؛ دروازهٔ نشانگر false آن را اجرا نمی‌کند.

دو [فایل سورس تصویری](../e2e/visual/website.spec.ts)، صحنه‌ها و
[انتظار آمادگی فونت](../e2e/visual/readiness.ts) را توصیف می‌کنند. تنظیم تصویر،
viewport، حرکت کاهش‌یافته، مرورگر و channel، نام تصویر و تلورانس پیکسلی موجود را
صریح نگه می‌دارد. به‌روزرسانی baseline در CI ممنوع می‌ماند. فراداده باید پلتفرم،
نسخهٔ SDK و مرورگر و بازبین و زمان واقعی و سازگار را نشان دهد. حالت update پیش
از تغییر تصویر، تأیید قبلی را بی‌اعتبار می‌کند؛ ضبط ناقص یا ناموفق باید در وضعیت
در انتظار بازبینی باقی بماند.

PNGها و فرادادهٔ Windows منتشرشده تاریخ و بایت تاریخی خود را حفظ می‌کنند. آن‌ها ورودی تصویر مبنا هستند و شاهد سازگاری فعلی نیستند. پذیرش برنامهٔ درخت دقیق باید ضبط و مقایسهٔ فعلی سازگار را طبق قرارداد تصویر اجرا کند؛ فرادادهٔ غایب یا ناسازگار شکست است. تاریخ را تازه نکنید و تصویر تغییریافته را بدون مجوز و بازبینی واقعی تأیید نکنید. [محدودیت تصویر](visual-regression.fa.md)، [فونت](fonts.fa.md) و [دسترس‌پذیری](accessibility.fa.md) را بخوانید.

دو فایل عملیات، [smoke انتشار](../e2e/operations/smoke.spec.ts) و
[پذیرش staging](../e2e/operations/staging.spec.ts) را شرح می‌دهند. این‌ها سناریوی
نوشته‌شده‌اند، نه گزارشی از تماس با محیط یا موفقیت آن.

## بررسی واقعی و کار باقی‌مانده

چهار فایل آزمون مالک Node در پوشش اندازه‌گیری‌شدهٔ راهبری و تحلیل سورس قرار
می‌گیرند. این آزمون‌ها ترتیب بررسی آمادگی با getter مسموم گزینه و محیط، manifest
مصنوعی SDK و برنامهٔ ساختگی CLI و ماژول متعلق به آزمون، رد ورودی نامعتبر، محتوای
تنظیم، توقف فرزند تحت مالکیت و مسیر شکست و پاکسازی را بررسی می‌کنند. این آزمون‌های
مالک مرورگر واقعی، برنامهٔ Next.js، API مستقل یا موتور Docker را راه نمی‌اندازند.
نوع SDK نصب‌شده در کامپایل سخت‌گیرانه شرکت دارد. پروفایل نشانگر false سناریوی
مرورگر را اجرا نمی‌کند و آن را موفقیت skipشده گزارش نمی‌دهد؛ پذیرش برنامه اجرای
واقعی و مستقل آن را می‌خواهد.

برای بررسی متمرکز توسعه می‌توان چهار مالک Node را اجرا کرد:

```sh
node --test scripts/browser-inputs.test.mjs scripts/playwright-config.test.mjs scripts/visual.test.mjs scripts/test-csp-report-only.test.mjs
```

پیش از commit، push یا تحویل PR مجاز، نصب تازهٔ Node و Python نسخه‌ثابت و [پروفایل کامل مرجع](../.agents/validation.json) پانزده‌بررسی باید روی درخت دقیق و ایزولهٔ برنامه موفق باشند. آستانهٔ واحد، راهبری و فونت، مجموعهٔ بستهٔ سورس و پیش‌بررسی کامل سرویس میزبان حفظ می‌شود. موارد مالک Node به‌تنهایی نتیجهٔ ساخت، مرورگر یا تصویر واقعی این نمایه را ثابت نمی‌کنند. [اعتبارسنجی](validation.fa.md)، [آزمون](testing.fa.md) و [پایداری آزمون](test-reliability.fa.md) مرجع‌اند.

فعال‌سازی برنامه باید صفحه، layout و CSS، تنظیم Knip، API مصنوعی مستقلاً نصب‌شده،
مرورگر آماده، baseline بازبینی‌شدهٔ مرتبط و job واقعی build، e2e و visual را فراهم
کند. پیش از ادغام نسخهٔ قابل اجرا، موفقیت واقعی این jobها را مشاهده و آن‌ها را
الزامی کنید. اجراکننده‌های محفوظ smoke در Docker و Lighthouse به پذیرش جداگانهٔ
عملیات تعلق دارند و جایگزین دروازهٔ برنامه نیستند. این مالکان،
[محدودیت اجراکننده‌ها](runner-foundation.fa.md)، از جمله مالکیت صرفاً فرزند مستقیم
به‌جای مدیریت همهٔ فرزندان بعدی را حفظ می‌کند و SSR، cookie در مرورگر، کیفیت تصویر
یا انتشار واقعی را ثابت نمی‌کند.
