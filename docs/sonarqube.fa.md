# SonarQube Cloud

[English](sonarqube.md) · [فارسی](sonarqube.fa.md)

[گردش‌کار موجود Sonar](../.github/workflows/sonar.yml) روی `ubuntu-latest`
اجرا می‌شود؛ در راه‌انداز سرویس **Linux** را انتخاب کنید، حتی اگر توسعهٔ محلی
روی ویندوز است. همین گردش‌کار را استفاده کنید و `build.yml` تکراری نسازید.
روش تحلیل در CI را انتخاب و تحلیل خودکار پروژه را خاموش کنید.

کلید پروژهٔ واردشدهٔ **`sepaseh_kernel-website`** را در variable اکشن
`SONAR_PROJECT_KEY` قرار دهید. پیش‌فرض `SONAR_HOST_URL` برابر
`https://sonarcloud.io` است. توکن دارای اجازهٔ تحلیل همین پروژه بسازید و
فقط مقدار آن را در Actions secret با نام **`SONAR_TOKEN`** ذخیره کنید.
برچسب توکن مانند `kernel-github-actions` دلخواه و جدا از نام secret و کلید
پروژه است. مقدار توکن را در سورس، dotenv، variable، چت یا log نگذارید.
نبود اعتبارنامه یا تنظیم پروژه خطای صریح می‌دهد و تحلیل ادعا نمی‌شود.

گردش‌کار مجموعهٔ دقیق فایل‌ها را بررسی، ابزارهای قفل‌شده را نصب و هر دو دستور
پوشش واقعی را پیش از اسکن اجرا می‌کند. [تنظیمات](../sonar-project.properties)
فایل‌های `coverage/unit/lcov.info` و `coverage/governance/lcov.info` را
از همان checkout و revision وارد می‌کند. پوشش مربوط به ابزارهای منتشرشده،
کاتالوگ‌های محلی و گردش‌کار است؛ رابط Next.js، مسیر HTTP، سفر مرورگر یا استقرار را پوشش نمی‌دهد.
تعریف صرف نوع DTO رفتار اجرایی ندارد. گزارش نسازید مگر از اجرای واقعی تست
و پوشش پروژهٔ دیگر را جایگزین نکنید.

اجرای واقعی، SHA یا PR تحلیل‌شده، تحلیل سرویس و دروازهٔ کیفیت را ثبت کنید.
scanner از `sonar.qualitygate.wait=false` استفاده می‌کند؛ ارسال موفق تحلیل
و سبزی job اکشن با موفقیت بررسی **SonarCloud Code Analysis** از App
`12526` متفاوت است. قبولی بررسی سرویس طبق
[حفاظت شاخه](branch-protection.fa.md) الزامی است. تحلیل غایب، اجرا‌نشده یا
ناموفق به معنی قبولی دروازهٔ کیفیت نیست.

پیکربندی و شمارندهٔ صفر خطا در پروژهٔ خالی شاهد اجرا نیستند. موفقیت CI اولیه و
دروازهٔ کیفیت Sonar برای [PR شمارهٔ ۱ وب‌سایت](https://github.com/sepaseh/kernel-website/pull/1)
در ۲۶ اکتبر ۲۰۲۶ تأیید شد؛ headهای بعدی به نتیجهٔ تازه نیاز دارند. خالی بودن
سابقهٔ main به‌تنهایی
مسدود بودن تحلیل PR نخست را ثابت نمی‌کند؛ خطای واقعی سرویس را بررسی کنید.
PR از fork اعتبارنامهٔ این گردش‌کار را دریافت نمی‌کند؛ اسرار را در اختیار
کد بررسی‌نشدهٔ fork قرار ندهید.

[محافظ فایل‌های PR](../scripts/check-pr-size.mjs) تعداد بیشتر از ۱۰۰ را از
metadata و پیش از درخواست فهرست فایل‌ها رد می‌کند. PR مجاز در یک پاسخ با
`per_page=100` جا می‌شود؛ هر پیوند صفحهٔ بعد ناسازگار است و بدون دنبال‌کردن
آن، بررسی با خطا متوقف می‌شود. محافظ تمام ورودی‌های پاسخ را اعتبارسنجی و پس از
دریافت، head، base و تعداد را دوباره بررسی می‌کند. این طراحی سیاست ۱۰۰ فایل را
صریح نگه می‌دارد و درخواست اضافی API را حذف می‌کند. نتیجه باید با تحلیل تازهٔ
سرویس تأیید شود؛ suppression یا تغییر طبقه‌بندی سرویس استفاده نمی‌شود.

[راهنمای رسمی GitHub Actions](https://docs.sonarsource.com/sonarqube-cloud/analyzing-source-code/ci-based-analysis/github-actions-for-sonarcloud)
و [روش‌های تحلیل](https://docs.sonarsource.com/sonarqube-cloud/analyzing-source-code/automatic-analysis)
را ببینید.

## پیش از درخواست بازبینی CodeRabbit

بازبینی اولیه یا مجدد را فقط وقتی درخواست کنید که **تمام بررسی‌های الزامی
غیر از CodeRabbit برای head دقیق و فعلی PR موفق شده باشند**. مجموعهٔ مصوب
هر مرحله را از [حفاظت شاخه](branch-protection.fa.md) بگیرید. مرحلهٔ منتشرشدهٔ
غیرقابل اجرا پیش از درخواست، موفقیت `check`، `SonarQube Cloud analysis`
و دروازهٔ کیفیت واقعی `SonarCloud Code Analysis` را لازم دارد. برای جلوگیری
از وابستگی دوری، فقط بررسی و تأیید خود CodeRabbit از این پیش‌شرط کنار گذاشته
می‌شوند.

طبق سیاست انتشار غیرقابل اجرا، jobهای برنامه با نام `build`، `e2e`
و `visual` اکنون الزامی نیستند. پیش از ادغام هر برنامهٔ قابل اجرا، این jobهای
واقعی را اضافه کنید، موفقیت اجرای آن‌ها را مشاهده کنید، آن‌ها را در بررسی‌های
الزامی قرار دهید و اعتبارسنجی کامل مرجع برنامه را گسترش دهید. job نمایشی
نسازید، بررسی الزامی را رد نکنید و ویرایش مستندات را تغییر سیاست دوردست ندانید.

آخرین تحلیل مرتبط PR یا شاخه در Sonar باید با همان head و محدودهٔ سورس
مطابقت داشته و **هیچ یافتهٔ OPEN یا حل‌نشده‌ای در هیچ سطح شدت**، از جمله
یافته‌های قبلی، نداشته باشد. سبز بودن دروازهٔ کیفیت یا صفر بودن یافتهٔ کد جدید
کافی نیست. فهرست کامل، فیلترها و صفحه‌بندی یافته‌ها را بررسی کنید. بررسی
غایب، در انتظار، اجرا‌نشده، ناموفق یا در دسترس‌نبودن، گزارش غایب یا نامنطبق
و نبود شاهد کامل صفر بودن یافته‌ها، درخواست بازبینی را مسدود می‌کند.

مثبت کاذبِ مستندشده در مخزن تا وقتی در سرویس OPEN است همچنان مانع است.
طبقه‌بندی درست و مجاز در سرویس یا
اصلاح واقعی کد همراه با تحلیل تازه باید در گزارش منعکس شود. برای دور زدن این
شرط، یافته را exclude یا suppress نکنید، wrapper صرفاً برای معیار نسازید و
بررسی‌ها را ضعیف نکنید.

head، نتیجهٔ بررسی‌های الزامی و تحلیل Sonar را ثبت کنید. commit یا تغییر head
جدید این شواهد را نامعتبر می‌کند. پس از اصلاح دوباره بررسی کنید، سهمیه را
رعایت کنید و برای head دارای بازبینی در حال اجرا، درخواست تکراری نفرستید.
فقط پس از تأمین تمام پیش‌شرط‌ها و با اجازهٔ صریح عملیات دوردست، یک درخواست
دستی بفرستید؛ بازبینی اجرا‌نشده یا محدود به سهمیه، بازبینی کامل نیست.
