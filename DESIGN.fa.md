# راهنمای طراحی وب‌سایت

[English](DESIGN.md) · [فارسی](DESIGN.fa.md)

این راهنما را همراه [روند طراحی](.agents/skills/design-ui/SKILL.md) و وظیفهٔ
design-ui در [ناوبری](.agents/navigation.json) بخوانید. سورس، اجزای نصب‌شده و
رفتار واقعی آن‌ها را تعیین می‌کند. این مرحلهٔ راهنما هنوز قابل اجرا نیست:
صفحه‌ها، layout ریشه، تنظیم مولد و ساخت CSS منتشر نشده‌اند. نام کلاس به معنی
سامانهٔ طراحی رندرشده یا کیفیت بصری تأییدشده نیست.

## سامانهٔ منتشرشده را بررسی کنید

برای صفحهٔ پیشنهادی، پیش از سبک‌دهی مسیر آینده، مالک قابلیت، کنش اصلی و حالت‌های
لازم را مشخص کنید. حالت‌های مرتبطِ بارگذاری، خالی، دارای داده، نامعتبر، خطا،
موفقیت، غیرفعال و بدون مجوز را پوشش دهید. گفت‌وگو و منو به رفتار واقعی صفحه‌کلید،
focus و بسته‌شدن نیاز دارند؛ تصویر آن رفتار را ثابت نمی‌کند.

## قرارداد برنامه را حفظ کنید

- قواعد [وب‌سایت](.agents/rules/website.md)، [import](.agents/rules/imports.md) و
  [ترجمه](.agents/rules/localization.md) را رعایت کنید. الگوی اجزای موجود و
  مجوز دقیق مالک هر بسته حفظ شود.
- [مالکیت نشست](docs/session.fa.md)، پاک‌سازی هنگام خروج از mount و guard پاسخ
  دیرهنگام را نگه دارید. ورود، مجوز، ارسال OTP، داده و ذخیره‌سازی متعلق به API
  مستقل است؛ نمونهٔ طراحی آن‌ها را پیاده نمی‌کند.
- فقط تنظیمات API زبان و جهت معتبر را انتخاب می‌کند. ده کاتالوگ تخت با ترجمهٔ
  واقعی، متغیر ICU و گروه صریح پیام کلاینت را حفظ کنید. انتخاب زبان بازدیدکننده
  اضافه نکنید؛ [راهنمای ترجمه](docs/localization.fa.md) را بخوانید.
- ترجیح تم، نام دسترس‌پذیر، focus دیدنی و حرکت کاهش‌یافته حفظ شود. بررسی واکنش‌گرا
  در آینده باید عرض کم و زیاد، هر دو جهت API، هر دو تم و ترجمهٔ بلند را پوشش دهد.
  این مرحله اجرای موفق مرورگر یا مقایسهٔ بصری را ثابت نمی‌کند.
- رفتار [مرز سرور](docs/server-boundary.fa.md)، [پشتیبانی سند](docs/client-document.fa.md)
  و [قلم](docs/fonts.fa.md) را استفاده کنید. صفحهٔ عمومی آینده باید مبدأ صریح SEO،
  JSON-LD ایمن، پاسخ خصوصی no-store و یکپارچگی CSP سند را حفظ کند. آزمون پشتیبان
  فعلی آن یکپارچگی را اثبات نمی‌کند.

## خروجی را انتخاب کنید

| خروجی درخواستی      | کار و شاهد لازم                                                                                                                                |
| ------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| تصویر یا ایدهٔ بصری | در صورت نیاز از ابزار موجود استفاده و دارایی، اندازه، شفافیت، مجوز و محل مصرف را ثبت کنید. ایده، کد تعاملی برنامه نیست.                        |
| طراحی ویرایش‌پذیر   | ابزار میزبان و skill مربوط را بررسی و اجزا، قلم، حالت‌ها و جهت واقعی را نگاشت کنید. مرجع طراحی و کار باقی‌مانده را ثبت کنید.                   |
| سورس برنامه         | از اجزای محلی و مالکان قابلیت استفاده کنید. مسیر، layout، تنظیم مولد و CSS متعلق به مرحلهٔ قابل اجرای بعدی است و گیت گسترده‌تر لازم دارد.      |
| نمونهٔ میزبانی‌شده  | دادهٔ ساختگی و محدودهٔ روشن داشته باشید. سازگاری واقعی سرویس را بررسی کنید. بارگذاری، اتصال مخزن و انتشار به مجوز همان اقدام بیرونی نیاز دارد. |

ابزار موجود را کشف کنید و وجود یکپارچه‌سازی را فرض نکنید. در کار عادی محلی سورس
یا دارایی خصوصی را بارگذاری نکنید. ابزار طراحی اختیاری وابستگی runtime نیست.
[CLAUDE.md](CLAUDE.md) و [واسط skill](.claude/skills/design-ui/SKILL.md) به راهنمای
مرجع اشاره می‌کنند؛ وجودشان ثابت نمی‌کند میزبان آن‌ها را بارگذاری یا سرویس طراحی
را تنظیم کرده است.

## بررسی و تحویل

شناسه‌های واقعی را از [manifest مرجع](.agents/validation.json) و با
[روند اعتبارسنجی](.agents/skills/validate-change/SKILL.md) انتخاب کنید. پیش از
commit، push یا تحویل PR مجاز، پروفایل کامل لازم است. شاهد سورس، آزمون واحد،
حاکمیتی و قلم این مرحله، چیدمان مرورگر، دسترس‌پذیری، SSR، build یا استقرار را
اثبات نمی‌کند. پیش از ادغام برنامهٔ قابل اجرا، بررسی واقعی build، مرورگر و بصری
باید اضافه و موفق شود.

خروجی، مالکان بررسی‌شده، اجزای استفاده‌شده یا تغییریافته، حالت‌های لازم، ابزارهای
واقعاً اجراشده، بررسی‌ها و مراجع بصری موجود را گزارش کنید. محدودیت API، دسترس‌پذیری
و میزبان را بنویسید. [راهنمای ارزیابی](docs/comprehension-evaluation.fa.md) کشف
مشاهده‌شدهٔ دستورها را از درک سورس و تأیید واقعی طراحی جدا می‌کند.
